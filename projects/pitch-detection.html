Signal Processing Project · LTH · 2026

Real-Time Pitch Detection

A real-time pitch detection system based on the YIN algorithm, implemented on Android and used as the control mechanism for an interactive mobile game.

Signal Processing YIN Java Android Real-Time Audio

Overview

The goal of the project was to investigate how smartphone audio input could be used as an interactive control method. We developed an Android game in which the player controls a moving bar using the pitch of their voice: higher frequencies move the bar upward and lower frequencies move it downward.

The central engineering challenge was therefore to estimate the fundamental frequency of microphone input accurately and fast enough for real-time interaction.

01

The Problem

Pitch corresponds to the fundamental frequency of a periodic signal. A straightforward approach is to use autocorrelation: a periodic signal resembles delayed versions of itself at lags corresponding to its period.

In practice, simply selecting the strongest autocorrelation peak is unreliable. Harmonics can produce strong peaks at multiples of the true period, and signal energy also affects the magnitude of the autocorrelation.

Design objective Detect vocal pitch reliably while keeping computation and latency low enough for smooth real-time gameplay.

02

Signal Processing Method

The pitch detector was based on the YIN fundamental-frequency estimation algorithm. The implementation uses three main steps.

1

Autocorrelation

The audio frame is compared with delayed versions of itself to identify periodic structure in the signal.

2

Difference Function

A squared-error measure is calculated between the original signal and shifted copies. Periodic matches appear as minima rather than peaks.

3

CMNDF

The error is normalized using the cumulative mean, reducing the bias toward short lags and making the fundamental period easier to identify.

Selecting the fundamental frequency

Choosing the global minimum of the normalized difference function can result in octave errors because minima also occur at multiples of the true period. Instead, the implementation searches for the first local minimum below a threshold of 0.15.

Once the best lag is found, the pitch is calculated as:

frequency = sample rate / lag

The search was restricted to frequencies between approximately 70 Hz and 1000 Hz, reducing unnecessary computation and focusing the algorithm on the relevant vocal-frequency range.

03

Real-Time Implementation

Audio was captured directly from the smartphone microphone using Android's AudioRecord interface. Incoming PCM samples were accumulated into an audio buffer and processed continuously by the pitch detector.

A noise threshold prevented very low-amplitude input from being interpreted as a valid pitch. To make the game movement less sensitive to individual estimates, groups of five pitch detections were averaged before updating the player's position.

04

Evaluation & Results

The implementation was evaluated both in terms of computational performance and pitch-estimation accuracy. Different sample rates, window sizes and audio-buffer sizes were tested to study the trade-off between computational cost and smooth gameplay.

Real-time performance

The final configuration required approximately 16.72 ms per pitch detection. Increasing either sample rate or window size produced an approximately linear increase in execution time, giving an empirical complexity of roughly:

O(sample rate × window size)

This processing time remained well below the 300 ms animation interval used by the game and did not produce a noticeable gameplay delay.

Across the tested range from D2 to A5, the detector tracked the reference frequencies closely. Performance became unstable near the algorithm's upper frequency boundary, illustrating the effect of the deliberately restricted lag search.

05

Engineering Trade-offs

The project highlighted that the most accurate signal-processing configuration is not automatically the best real-time configuration. Higher sample rates and larger windows provide greater frequency resolution and smoother control, but increase computational cost.

For this application, the final parameters were selected to prioritize stable and responsive gameplay rather than laboratory-grade frequency estimation.

One remaining limitation was sensitivity to background noise. An amplitude threshold improved robustness, but reliable operation still required a relatively quiet environment.

06

Key Takeaways

This project provided practical experience taking a signal processing algorithm from theory to a real-time application: deriving and implementing the pitch estimator, selecting computational parameters, processing live microphone data, evaluating performance and integrating the resulting signal into an interactive Android application.
